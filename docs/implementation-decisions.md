# Implementation decisions

The master spec is preserved verbatim from the user-supplied Markdown. The original remote repo had only README.md. The separate initial architecture review remains a proposal; this file records implementation refinements.

1. **Scope:** The user authorized proceeding to M1 while M0 had not been implemented. Build required M0 foundations and M1 together; verify both sets of gates before handoff. Do not advance to M2 without confirmation.
2. **Deployment:** Structured Next.js 16 app, React/TypeScript, Node 24 runtime image, PostgreSQL 17 in Compose. No required proxy or TLS. Node 25 is the available local test host; CI verifies Node 24. PostgreSQL-backed integration tests run a disposable native PostgreSQL distribution, not SQLite.
3. **Data access:** Reviewed SQL migrations are the schema source of truth. Parameterized node-postgres transactions enforce domain rules. Drizzle's PostgreSQL adapter is available through `lib/db.ts`; SQL is used directly where row/advisory locking and explicit returning clauses matter. This avoids a second schema generator competing with hand-reviewed migrations.
4. **UI:** Locally owned accessible native dialog/form/table primitives and semantic CSS tokens, rather than adding Tailwind/shadcn before the component boundaries are stable. Matches the specification's dimensions, typography, muted accent, light/dark/system modes and phone targets. This is a tooling choice; product UI guidelines remain requirements. Future sections are noninteractive roadmap text; only functioning M1 navigation/actions appear.
5. **Onboarding:** Owner/business configuration is one validated first-run form, followed by Settings storage/backup and optional vault setup. Vault creation is not required for basic HTTP use. No fake SMTP form before M3. A bootstrap token prevents unprotected LAN first-claim setup.
6. **Vault storage:** Versioned password/recovery envelopes are strict JSONB columns on the singleton vault row, atomically updated together; the current encrypted structured payload is strict JSONB on each credential. Separate audit and nonce-history tables retain boundaries. This replaces proposed separate envelope/payload tables for the initial one-generation design. All fields are validated; no secret scalar columns are introduced.
7. **Vault memory:** Component-scoped VMK ref, byte clearing and operation epochs. Navigation away and tab hidden lock immediately. No worker yet; no memory-erasure guarantee. Master-key rotation is designed but not implemented in M1; password rewrap and recovery are implemented. Generation changes require a separate tested migration/rotation workflow.
8. **Crypto:** Argon2id memory 64 MiB / passes 3 / lanes 4 and versioned HKDF + AES-GCM. No HTTP crypto polyfill. Browser/dependency review is a release gate for actual client secrets. M1 test values are fictional. Clipboard errors cannot report success; camera/QR decode local only.
9. **General HTTP:** Idempotency request IDs are generated server-side, avoiding reliance on browser `crypto.randomUUID`, which is unavailable in ordinary insecure contexts. This preserves client/work/timer operations without weakening vault requirements.
10. **Work:** Activities require a client and never require a job. Time-entry rate/rounding snapshots persist; running timer snapshots rates at start. Stops are idempotent, pause intervals preserved, and one paused/running timer per owner is enforced in PostgreSQL. Invoice application of rounding and job rate hierarchy arrive with M2.
11. **Notes:** Contextual safe Markdown, raw HTML skipped. All context references use enforced concrete FKs. No standalone notebook or HTML execution.
12. **Backup:** Domain mutations acquire a shared advisory transaction lock; backup holds exclusive lock while dumping DB and copying files. Sessions may update ephemeral timestamps during capture. Dumps include vault ciphertext/envelopes. Deployment keys are outside manifest. Retention/off-host scheduling remain later work; recovery rehearsal must also be performed after fresh restore.
13. **Fictional seed:** Opt-in, empty-client-list only, no default owner/vault. Never seed production credentials.
14. **Delivery:** Existing GitHub CLI account has repository admin/write access, even though connector access is read-only. Use CLI fallback for authorized push/CI inspection; no force push. Validate on a temporary branch before advancing main. No real client credentials are used during testing.
