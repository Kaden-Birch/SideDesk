# Implementation decisions

The master spec is preserved verbatim from the user-supplied Markdown. The original remote repo had only README.md. The separate initial architecture review remains a proposal; this file records implementation refinements.

1. **Scope:** The user authorized proceeding to M1 while M0 had not been implemented. Build required M0 foundations and M1 together; verify both sets of gates before handoff. The user subsequently confirmed M2; M3 was subsequently authorized; stop after its handoff until M4 is authorized.
2. **Deployment:** Structured Next.js 16 app, React/TypeScript, Node 24 runtime image, PostgreSQL 17 in Compose. No required proxy or TLS. Node 25 is the available local test host; CI verifies Node 24. PostgreSQL-backed integration tests run a disposable native PostgreSQL distribution, not SQLite.
3. **Data access:** Reviewed SQL migrations are the schema source of truth. Parameterized node-postgres transactions enforce domain rules. Drizzle's PostgreSQL adapter is available through `lib/db.ts`; SQL is used directly where row/advisory locking and explicit returning clauses matter. This avoids a second schema generator competing with hand-reviewed migrations.
4. **UI:** Locally owned accessible native dialog/form/table primitives and semantic CSS tokens, rather than adding Tailwind/shadcn before the component boundaries are stable. Matches the specification's dimensions, typography, muted accent, light/dark/system modes and phone targets. This is a tooling choice; product UI guidelines remain requirements. Future sections are noninteractive roadmap text; only functioning navigation/actions appear.
5. **Onboarding:** Owner/business configuration is one validated first-run form, followed by Settings storage/backup and optional vault setup. Vault creation is not required for basic HTTP use. No fake SMTP form before M3. A bootstrap token prevents unprotected LAN first-claim setup.
6. **Vault storage:** Versioned password/recovery envelopes are strict JSONB columns on the singleton vault row, atomically updated together; the current encrypted structured payload is strict JSONB on each credential. Separate audit and nonce-history tables retain boundaries. This replaces proposed separate envelope/payload tables for the initial one-generation design. All fields are validated; no secret scalar columns are introduced.
7. **Vault memory:** Component-scoped VMK ref, byte clearing and operation epochs. Navigation away and tab hidden lock immediately. No worker yet; no memory-erasure guarantee. Master-key rotation is designed but not implemented in M1; password rewrap and recovery are implemented. Generation changes require a separate tested migration/rotation workflow.
8. **Crypto:** Argon2id memory 64 MiB / passes 3 / lanes 4 and versioned HKDF + AES-GCM. No HTTP crypto polyfill. Browser/dependency review is a release gate for actual client secrets. M1 test values are fictional. Clipboard errors cannot report success; camera/QR decode local only.
9. **General HTTP:** Idempotency request IDs are generated server-side, avoiding reliance on browser `crypto.randomUUID`, which is unavailable in ordinary insecure contexts. This preserves client/work/timer operations without weakening vault requirements.
10. **Work:** Activities require a client and never require a job. Time-entry rate/rounding snapshots persist; running timer snapshots rates at start. Stops are idempotent, pause intervals preserved, and one paused/running timer per owner is enforced in PostgreSQL. M2 implements invoice rounding and job/entry rate hierarchy.
11. **Notes:** Contextual safe Markdown, raw HTML skipped. All context references use enforced concrete FKs. No standalone notebook or HTML execution.
12. **Backup:** Domain mutations acquire a shared advisory transaction lock; backup holds exclusive lock while dumping DB and copying files. Sessions may update ephemeral timestamps during capture. Dumps include vault ciphertext/envelopes. Deployment keys are outside manifest. Retention/off-host scheduling remain later work; recovery rehearsal must also be performed after fresh restore.
13. **Fictional seed:** Opt-in, empty-client-list only, no default owner/vault. Never seed production credentials.
14. **Delivery:** Existing GitHub CLI account has repository admin/write access, even though connector access is read-only. Use CLI fallback for authorized push/CI inspection; no force push. Validate on a temporary branch before advancing main. No real client credentials are used during testing.

15. **M2 financial records:** Drafts reserve full stopped time entries using a partial unique active-allocation index and source row locks. No partial time allocation in this milestone. Issuance locks the invoice and singleton counter; PDF generation, stored bytes/hash, issued snapshot and counter increment share one transaction. This favors consistency over renderer throughput. Rendering is bounded; failure rolls back without consuming a number. PostgreSQL triggers freeze issued headers/lines and allocated time and make payments/events/revisions append-only. Database administrators can still bypass application controls; this is auditability, not tamperproof storage.
16. **M2 rate/math:** Entry override → historical job → client → business, snapshotted at recording/timer start. Existing M1 rows retain legacy snapshots. Group rounding requires matching historical job/rate/increment/scope; entry rounding applies individually. BigInt rational arithmetic rounds cents half-up after discount and then tax. CAD only. Receipts do not edit the issued total; balance is derived from receipts less full error reversals. Full credits/refunds and tax rules remain M3.
17. **M2 documents:** Pinned Playwright/Chromium HTML-to-PDF, escaped text, validated accent, no user HTML, JavaScript disabled and network blocked. Fresh context/browser per render, bounded time/concurrency. Issued PDFs are DB bytea rather than filesystem references so number/snapshot/document commit atomically and backup consistently. A4/Letter templates use repeated table headings/page counts. Logo upload is deferred; identity/accent are configurable. No remote image loading.
18. **M2 files:** Job attachments use opaque UUID names in the private upload volume, owner-only attachment downloads, 10 MB limit, non-following reads, size/SHA validation and soft archive. Files are ordinary business documents, not encrypted vault payloads. Storage writes participate in backup locking; crash-orphaned files may remain and are harmless private bytes. No server-side preview/antivirus or vault-secret attachment support is claimed.
19. **M2 navigation/deployment:** Jobs and Sales now have working pages; Quotes are described as unavailable rather than an inert tab. Chromium and Linux dependencies ship inside Docker. Standalone development packaging explicitly retains Playwright runtime resources. M2 schema rollback to M1 is unsupported; use version-compatible fresh restores. Deployment secrets and vault envelopes retain the existing persistence contract.

20. **M3 quotes:** Publish freezes a dedicated quote document/PDF and locked quote number. Published and SMTP-sent are distinct states. Explicit evidence is required for acceptance/decline. Conversion copies the accepted manual-line snapshots into a job/invoice; no current tax/rate repricing. One active invoice per quote is enforced by a partial unique index. Discard/void permits a replacement while preserving historical links. Quote-first/invoice-second locking serializes conversion and replacement. Changed scope/prices in a saved draft are compared with the accepted reference.
21. **M3 tax/corrections:** Versioned profile components use integer thousandths of a percentage point, with independent or explicitly compounded bases. Cents round half-up per component per line. Zero/exempt treatments persist. Credits record total plus explicit included tax; tax and pretax limits are enforced. Refunds are cash events, not a second tax adjustment. Live balances derive from append-only receipts/adjustments; original invoice snapshots/PDFs remain unchanged. Sent/refund-due/settled statuses are derived from events and balances.
22. **M3 costs:** CAD vendor cost and customer recovery are separate fields/entities. Mileage and travel labour create distinct full client charges from historical input/rate snapshots. Charge allocations and source locks prevent duplication/partial billing and protect allocated expenses/trips. Cost revisions preserve reasons and before/after records. Private receipt handling reuses the job-file boundary. M4 must link stock acquisitions to a single existing expense/purchase outflow, not create duplicate spending.
23. **M3 SMTP:** Pinned Nodemailer SMTP only, verified TLS/required STARTTLS, disabled file/URL attachment access, bounded connection/socket settings and no raw transport logging. Dedicated 32-byte deployment key encrypts the server-managed SMTP password with versioned AES-GCM and purpose/singleton AAD. No vault-key or SESSION_SECRET fallback. Optional read-only private CA file is deployment configuration. Plain relay is explicitly unauthenticated only. Attempt intent/hash/idempotency is committed before external sending; accepted/failed/unknown results append separately. Pending/unknown attempts are never auto-retried after crashes/restores. Server acceptance does not prove delivery or client agreement.
24. **M3 delivery:** Preserve all M0–M2 gates; local TLS SMTP fixtures contact no real recipients. Compose CI exercises new quote/PDF, cost/receipt/trip allocations, credit/refund balances and encrypted SMTP settings across a fresh restore. Code downgrade to M2 after migration 0003 is unsupported. Independent cryptographic review remains required before actual client secrets.
